# CryoSat

NeoForge 1.21.1 addon for Mekanism 10.7 (cryogenics plus orbital/space content). Parchment mappings
on top of Mojang names. Java 21. Package `io.github.valajar.cryosat`, mod id `cryosat`.

## Build and verify

* `./gradlew build` must pass before committing.
* There is no game client in cloud sessions. Verify behaviour with game tests:
  `./gradlew runGameTestServer` runs every `@GameTestHolder` class in
  `io.github.valajar.cryosat.gametest` headless and exits (non zero on failure). Tests use the
  1x1x1 `cryosat:empty` structure unless they need a real arena. `runServer` does not receive
  stdin through Gradle, so it never stops on its own.
* CryoSat deliberately builds on Mekanism internals (`mekanism.common.*`, `mekanism.client.*`):
  machines extend Mekanism's tile, container and GUI classes to get native side config, upgrades,
  security and the Mekanism look, and multiblocks use `mekanism.common.lib.multiblock`. Internals
  can change in any Mekanism release, so `mekanism_version` in `gradle.properties` is the single
  tested version and the mods.toml range stops at the next minor. Bumping Mekanism means bumping
  that property and running the game tests. Prefer `mekanism.api.*` where it covers the need.
* Use Generators (`mekanism.generators.*`) as the reference for how an addon registers blocks,
  tiles, containers and multiblocks through Mekanism's registration helpers.

## Conventions

* Registries live in `io.github.valajar.cryosat.registries`, one class per registry, each
  registered from the `CryoSat` constructor. Blocks, block entities, menus and items use
  Mekanism's registers like Generators does: `CryoBlockTypes` (Mekanism `Machine`/`BlockTypeTile`
  attributes), `CryoBlocks` (`BlockDeferredRegister`, registers the block items too),
  `CryoBlockEntities` (`TileEntityTypeDeferredRegister.mekBuilder`, which also registers the
  capabilities), `CryoMenus` (`ContainerTypeDeferredRegister`), `CryoItems`
  (`ItemDeferredRegister`). `CryoChemicals` stays a plain `DeferredRegister`.
* Chemicals go into Mekanism's chemical registry (`MekanismAPI.CHEMICAL_REGISTRY_NAME`) so they
  work with Mekanism tubes and tanks.
* Lang keys: chemicals use `chemical.cryosat.<name>`.
* Data generation (`./gradlew runData`, providers in `datagen/`) owns blockstates, block and item
  models, lang, loot tables, tags and recipes; its output in `src/generated` is committed. Hand
  written JSON only for Blockbench models and our own datapack types (e.g. atmospheres). Run it
  after adding textures, since it validates that referenced textures exist.
* Machines extend Mekanism's `TileEntityConfigurableMachine` (side config, ejector, upgrades,
  redstone, security) with a `BlockTile` block and a `GuiConfigurableTile` screen registered in
  `client/CryoSatClient`; `machine/compressor` is the worked example (block type, block with item
  attachments and default side config, tile type, menu, GUI, lang, loot via
  `CryoBlockLoot.dropMachine`). Fields assigned in `getInitial*` must not have initialisers.
  Status reasons shown in GUIs use `machine.MachineStatus`. Mekanism items in recipes are
  referenced by id or `c:` tags, never by class.
* Atmospheres for the Atmospheric Compressor are datapack files in
  `data/<ns>/cryosat/atmosphere/`.

## Textures and models

Read `docs/texture-style-guide.md` before touching any PNG or model JSON. Textures are generated by
deterministic Python scripts in `tools/textures/gen/` using `tools/textures/texlib.py` and the
palette in `tools/textures/palette.py`. Always render a preview with `tools/textures/preview.py`
next to Mekanism references and look at it before committing.
